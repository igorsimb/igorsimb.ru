I Wanted a Flexible SQL Agent. I Didn’t Want to Trust the LLM.

TL;DR

Dux lets the model propose the SQL each question requires. Deterministic application code validates the exact query, decides where it may run, and owns the result rows.

I do not trust LLMs.

This is slightly inconvenient because I am building an application that asks one to write SQL against business data.

I like working with LLMs, and I am increasingly building my work around them. But they hallucinate. They invent details and make non-obvious decisions under the hood.

That is manageable when the model is helping me brainstorm a name. It becomes more uncomfortable when it is answering a business question from a database.

A plausible but incorrect answer is often worse than an obvious failure. It looks finished. It has numbers. Someone can act on it without realizing that the model joined the wrong tables or made an assumption the user never intended.

My answer became Dux with a simple premise:

LLM writes SQL. Code decides if it runs.

A perfectly valid solution to a different problem

Before I settled on that approach, I spoke with a developer who had already built a system for answering questions from company data.

His approach was more constrained. He knew the industry, understood the questions users asked repeatedly, and prepared the data around those questions. The model acted as a natural-language interface over a known set of capabilities.

It was controlled, predictable, and a good fit for what his company needed. The trade-off was that a new kind of question could require another development task.

I did not know the business domain well enough to anticipate every useful question. If I could not list those questions in advance, I needed to let the model construct new queries.

What happens after the question

The visible interaction looks simple. Underneath it, Dux separates what the LLM may propose from what the application will authorize.

The model gets a limited view of the data

Dux does not expose every table it can physically reach. The model sees an allowlisted catalog with source, dialect, table grain, useful columns, join relationships, and query hints.

Code validates the exact query

The proposed SQL goes through a backend-owned validation path. Dux checks that it is read-only, parses it using configured dialect candidates, resolves table references against source-specific allowlists, and applies metadata policy.

Validation creates a capability

When the query passes validation, Dux stores the normalized SQL together with the source and dialect selected by the backend. It returns a short-lived, thread-bound, one-time validated_id.

execute_validated_sql(validated_id)

The execution tool does not accept another SQL string from the model. The approved query is already stored and can be consumed only once.

The backend owns the visible rows

Dux converts the SQL response into backend-owned structured table blocks. The model can write commentary and give the table a useful title. It cannot supply or modify the visible rows.

The sources of authority remain explicit:

  • The model proposes the query.
  • Code decides whether that exact query may run.
  • The database produces the rows.
  • The backend preserves those rows.
  • The model explains them.

The extra complexity is real

Dux needs source configuration, table metadata, dialect-aware parsing, candidate routing, allowlist enforcement, capability storage, expiration rules, structured result assembly, permission filtering, and tests around all of it.

That is more machinery than exposing five carefully written query functions. I think it is worth it for the problem I am trying to solve, but it is not the right trade-off for every application.

What Dux is today

Dux is working software in active development. The core path described here exists, can be run against the bundled Chinook database, and has focused deterministic tests.

What I do not have yet is evidence from independent users or production workloads. Tests give me confidence that the boundaries behave as designed. They do not prove that I designed every boundary correctly.
